# 大湾区航空 · 企业智能分析平台 — 项目总结

> 品牌：**大湾区航空（Greater Bay Airline）**
> 定位：把决策从「拍脑袋」变成「根据数据来决策」的企业数字化转型多表数据分析决策平台
> 前身：CRM 自然语言数据库查询智能体（单表查询工具）→ 升级为**多表、多指标、带建议**的决策助手

---

## 1. 项目概述

用户不需要编写 SQL，只需用中文自然语言提问，系统会自动完成：

```
中文问题 → 生成 SQL / 调用业务工具 → 安全校验 → 真实执行 MySQL → 指标计算 → 自然语言回答 + 决策建议
```

两个业务子系统共用同一套平台能力：

| 子系统 | 性质 | 核心能力 |
| --- | --- | --- |
| A. 航空运营分析 | 练手 / 演示 | 客座率、毛利率、打折建议（多表 JOIN 分析） |
| B. 人力分析：人才流失预测与干预 | **核心交付** | 考勤 + 工资 + 考评 → 人才画像 → 升/育/留/裁建议 |

> **关键原则：答案 100% 来自数据库真实查询结果，AI 不做凭空猜测；业务建议由后端规则引擎基于真实数据计算，可解释、稳定、不额外消耗 token。**

## 3. 系统架构

```
User（浏览器 Chat / 业务看板 / HR 看板）
   ↓ 中文问题（可带 sessionId 多轮记忆）
Frontend（React + Vite + Tailwind + recharts）
   ↓ POST /api/chat
Backend API（Express + TypeScript）
   ↓ 获取数据库 Schema（7 张表 + 外键关系）
AI 数据库 Agent（Function Calling 多步分析，最多 8 轮）
   ├── execute_sql 工具：只读 SELECT，支持多表 JOIN（规避 JOIN 聚合陷阱）
   ├── employee_profile / suggest_action 工具：人才画像 + 升/育/留/裁（调规则引擎）
   ├── airline_suggestion 工具：打折建议（调规则引擎）
   └── 反复执行，基于真实结果输出回答 + 结构化 suggestion
   ↓ 每个 SQL 都经过 SQL 安全校验（Parser + 黑名单 + 表名白名单）
MySQL（7 张表：航空 2 + 员工主数据 1 + 人力流水 3 + CRM 保留）
   ↓ 真实查询结果
Frontend（回答 + 查看 SQL + 结果表 + 建议卡片 + 历史记录）
   ↓
看板（管理员专属）：业务看板（客座率 vs 平均票价 双 Y 轴）/ HR 看板（人才画像）
```

## 4. 数据模型（7 张表）

### 航空运营（2 表）

```sql
airline_flight_t   -- 航班表：FLIGHT_ID, ROUTE, AIRPLANE_MODEL, TOTAL_SEATS, OPERATING_COST, FLIGHT_DATE, STATUS
airline_booking_t  -- 订票表：ORDER_ID, FLIGHT_ID(FK), PASSENGER_NAME, TICKET_PRICE, BOOKED_AT
-- 关系：FLIGHT_ID 1:N；指标口径：客座率 = 订票数 ÷ 总座位数；毛利率 = (收入 − 成本) ÷ 收入
```

### 人力分析（统一员工主表 + 3 张流水表）

```sql
crm_employee_t     -- 员工主数据：ID, NAME, GENDER, SALARY, DEPARTMENT_NAME, EMAIL, ADDRESS,
                   --             POSITION, HIRE_DATE, STATUS, PERFORMANCE_LEVEL(A/B+/B/C)
hr_attendance_t    -- 考勤：EMPLOYEE_ID, ATTEND_DATE, STATUS(present/leave/late/absent)
hr_salary_t        -- 工资流水：EMPLOYEE_ID, SALARY_MONTH, BASE_SALARY, BONUS, DEDUCTION, NET_SALARY
hr_review_t        -- 考评：EMPLOYEE_ID, REVIEW_DATE, SCORE_LEVEL, SCORE, COMMENT
-- 关系：crm_employee_t.ID 关联三张流水表（1 员工 : N 记录）
-- 口径：hr_salary_t.BASE_SALARY = crm_employee_t.SALARY（问数系统与 HR 系统工资一致）
```

> **关键设计**：员工主数据统一为 `crm_employee_t`（100 人 / 10 个部门），每人都有考勤、工资流水与 2 期考评。「问数系统」「Admin 数据管理」「HR 画像/看板」人员完全一致。

### 演示数据规模（`npm run db:seed`，幂等重建、可复现）

| 表 | 规模 |
| --- | --- |
| airline_flight_t | 368 航班（4 条航线 × 92 天，2026-06-01 ~ 08-31） |
| airline_booking_t | 24,290 张订单（8 月促销月：上座 50%~80%、票价 5.5~8 折） |
| crm_employee_t | 100 名员工 / 10 个部门 |
| hr_attendance_t / hr_salary_t / hr_review_t | 6,600 条考勤 / 300 条月薪 / 200 条考评 |

## 5. 核心功能

### 5.1 自然语言 → SQL（数据库 Agent，Function Calling 工具循环）

- LLM 可反复调用 `execute_sql` 探查数据、逐步分析，最多 8 轮；每轮 SQL 都过安全校验。
- 系统提示词注入**全部表 Schema + 外键关系**，LLM 自动生成多表 JOIN。
- 内置 **JOIN 聚合陷阱提示**：教 LLM 先子查询聚合订单数再与航班表 JOIN，避免 `SUM(TOTAL_SEATS)` 被放大导致客座率算错。

### 5.2 业务规则引擎（决策建议）

`backend/src/services/businessRules.ts` 基于真实数据计算，输出结构化建议：

| 功能 | 规则 |
| --- | --- |
| 客座率 / 毛利率 | 订票数 ÷ 总座位数； (收入 − 成本) ÷ 收入（子查询预聚合） |
| 打折建议 | 促销月(8月) vs 平时(6-7月) 票价弹性 → 折扣取整到 5%，输出依据/预期效果/风险 |
| 人才画像 | 在岗率/请假率/迟到/旷工 + 工资与部门均值对比 + 考评趋势 → 5 种标签 |
| 流失风险分 | 加分制：绩效下滑 +20、请假率>10% +15、旷工≥2 +25、低薪 +20、长期未晋升 +10、绩效优低薪 +15 |
| 升/育/留/裁 | 力争上游→升（加薪 20%）；流失风险→育（加薪+放权）；稳定→留；边缘化→裁 |

LLM 通过 `employee_profile` / `suggest_action` / `airline_suggestion` 工具调用规则引擎，建议以**前端建议卡片**展示。

### 5.3 看板（仅管理员可见）

- **业务看板 · 航空**：航班数/客座率/收入/毛利率指标卡 + 低客座率航线 Top4 + **双 Y 轴图表**（左轴客座率 0-100%，右轴平均票价 ¥，两条曲线对比促销效果）+ 打折建议卡。
- **HR 看板 · 人才**：员工总数/在岗率/请假率 + 绩效分布 / 流失风险 Top5 / 干预动作分布 / **部门对比表**（请假率排序）。
- RBAC：两个看板接口均挂 `requireAuth + requireRole('admin')`，普通用户看不到导航、接口返回 403。

### 5.4 多轮对话记忆

- 前端维护 `sessionId`（localStorage 持久化），Chat 顶部「新对话」按钮可开启全新会话。
- 后端 `sessionStore`（内存版，容量上限自动淘汰，独立接口可替换为 Redis）按会话保存最近若干轮问答，真实 LLM 模式注入上下文，支持「那她呢？」等指代追问。
- 实测：Q1「唐佳琪的绩效和出勤怎么样？」→ Q2「那她该怎么处理？」正确指代并给出"裁"建议。

### 5.5 安全设计

1. SQL 只读白名单：node-sql-parser 解析 AST，根节点必须为 select
2. 关键字黑名单（INSERT/UPDATE/DELETE/DROP/ALTER/... 一律拒绝）
3. 禁止多语句（分号即拒绝）
4. 禁止系统表（mysql.* / information_schema.* / performance_schema.*）
5. 表名白名单：只允许 Schema 中真实存在的表
6. 写操作仅 admin + 参数化 SQL
7. API Key / 数据库密码不入库、不打印日志、不回传前端

### 5.6 其他复用能力

- **Excel 导出/导入**：结果导出弹窗（部门过滤 + 姓名搜索 + 列选择）、智能导出建议（规则闸门 + 偏好记忆）、Admin 批量导入（参数化 upsert，幂等）。
- **RBAC + 登录**：admin（管理员/老板，可看板 + 增删改数据）/ user（只读查询）。
- **Mock 模式**：无 API Key 时规则生成 SQL（真实执行，不编造数据）；业务问题（画像/建议/看板/在岗率）直接命中规则引擎。
- **历史记录**：Question / SQL / Answer / 耗时，可重问。

AI 模式：`AI_MOCK_MODE=false` 走真实 DeepSeek（Settings 页可切换）；无 Key 时开 Mock 模式同样能回答核心业务问题。

## 11. 关键问题与解决（经验沉淀）

1. **JOIN 聚合放大陷阱**：航班表与订单表 JOIN 后 `SUM(TOTAL_SEATS)` 被订单数放大 → 客座率错误。解决：子查询按 FLIGHT_ID 预聚合订单数再 JOIN；并在 Agent 提示词中明示该陷阱，LLM 生成的 SQL 不再踩坑。
2. **两套员工数据不一致**：CRM 100 人 vs HR 30 人 → 合并为统一员工主表 `crm_employee_t`（含 HR 属性），流水表挂到 `ID`，全系统一套人。
3. **复杂问题只查一次 SQL 答不出来** → Function Calling 工具循环（最多 8 轮），LLM 可取样、探查、聚合多步分析。
4. **LLM 建议不可解释/不稳定** → 业务建议改由后端规则引擎计算（确定、可解释），LLM 只负责组织语言。
5. **无记忆** → sessionStore 内存会话存储 + 前端 sessionId，真实模式注入上下文。
6. **node-sql-parser ESM 兼容 / v5 API 变更** → `import sqlParser from 'node-sql-parser'` + `.parse().ast`。
7. **tsx 模块热重载不完整** → 修改后需手动重启后端；tsx watch 大部分情况可自动重载。
